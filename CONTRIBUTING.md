# Contributing — jak rozwijać qa-tools

## Jak dodać nowy obszar pipeline'u (np. `foo`)

Każdy obszar = **4 subagenty** (`planner → writer → refactor → code-reviewer`). Wzorzec: `a11y`, `security`.

1. **4 pliki agentów** w `.vibe/plugins/qa-tools/ai.mistral.vibe/agents/`:
   - `foo-test-planner.toml`, `foo-test-writer.toml`, `foo-test-refactor.toml`, `foo-test-code-reviewer.toml`
   - schemat kluczy (snake_case — runtime `_PluginAgentDocument` odrzuca camelCase):
     `schema_version = 1`, `agent_type = "subagent"`, `display_name`, `description`, `safety`, `instructions`, `enabled_tools`, `disabled_tools`
   - `instructions` muszą zawierać konwencje qa-tools: nazewnictwo `should <rezultat> when <warunek>`, asercje tylko `await expect(...)` (zakaz `waitForTimeout` dla etapów writer/refactor/code-reviewer obszarów UI-owych), selektory `getBy*`, plannerzy zapisują plany do `docs/scenarios/<obszar>/`
2. **Walidator**: dodaj obszar do `PLAYWRIGHT_AREAS` w `scripts/validate-plugin.py` (i ewentualnie do wykluczeń reguły `waitForTimeout` dla obszarów nie-UI, jak `api`/`contract`/`db`).
3. **README.md**: wiersz w tabeli obszarów, 4 linie w drzewku `agents/`, aktualne liczby w intro (`**NN subagentów**`) i komentarzu struktury — walidator to sprawdza.
4. **CHANGELOG.md** + **`.vibe/plugins/qa-tools/plugin.json`**: bump wersji (minor = nowy obszar/skill) i wpis — walidator wymaga zgodności wersji.
5. **Testy**: `python -m unittest discover -s tests -v` i `py scripts/validate-plugin.py` — oba muszą przejść (CI też to robi).
6. Commit + push. Tag `vX.Y.Z` i release powstają automatycznie (patrz niżej).

## Jak dodać skill

1. Katalog `.vibe/plugins/qa-tools/skills/<nazwa>/SKILL.md` z frontmatter: `name`, `description`, `user-invocable: true`.
2. README: liczba skillów w intro i komentarzu struktury (walidator sprawdza zgodność).
3. Bump minor + CHANGELOG + walidator + testy.

## Zasady

- Commity: opisowe, po angielsku, z dopiskiem `Generated by Mistral Vibe. Co-Authored-By: ...`.
- **Emoji w skillach — konwencja**: każdy nagłówek `##` w `SKILL.md` zaczyna się od jednej tematycznej emotki (np. `## 🧪 What to test`, `## ⚠️ Common pitfalls`, `## ✅ Checklist`, `## 🚨 Red flags`). Przykłady good/bad oznaczamy `✅ DOBRY:` / `❌ ZŁY:`. Emotka jest znacznikiem, nigdy jedynym nośnikiem znaczenia (dostępność — screen reader). Bez przesady: jedna na nagłówek, nie w każdej linijce.
- Żadnych sekretów w repo (`.env`, tokeny) — payloady testowe tylko fikcyjne.
- `py scripts/validate-plugin.py` exit 0 przed każdym commitem; CI (`validate-plugin.yml`) pilnuje tego na push/PR.

## Release

Release są **automatyczne**: workflow `.github/workflows/release.yml` przy każdym pushu do `main` czyta najnowszy wpis `## [x.y.z]` z `CHANGELOG.md` i jeśli tag `vx.y.z` jeszcze nie istnieje — tworzy tag oraz GitHub Release z notatkami z tej sekcji CHANGELOG. Wystarczy więc: wpis w CHANGELOG + bump `plugin.json` + push.

Ręcznie (awaryjnie, np. release dla starego taga):

```bash
sed -n '/^## \[1.5.0\]/,/^## \[1.4.0\]/p' CHANGELOG.md | sed '1d;$d' | gh release create v1.5.0 --title "qa-tools v1.5.0" --notes-file -
```

## Issues

Bugi i propozycje ficzerów zgłaszamy przez issue templates: `.github/ISSUE_TEMPLATE/bug_report.md` i `.github/ISSUE_TEMPLATE/feature_request.md`.
