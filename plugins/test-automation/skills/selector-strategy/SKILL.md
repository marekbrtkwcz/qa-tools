# Selector Strategy

Selectors are the contract between the test and the UI. A fragile selector strategy makes the suite expensive to maintain; a self-healing layer on top makes failures silent. This skill decides the strategy once, per project.

## Operating Principles

- **Selectors should test what the user perceives, not how the DOM is built.** Role, label and text are user-facing; CSS classes and XPath are implementation details.
- **`data-testid` is a deliberate contract, not a dumping ground.** Add it in the component where the element matters, named after the action (`checkout-submit`), never auto-generated per render.
- **Self-healing hides regressions.** If a locator healer finds the button by fuzzy text match, a renamed button passes silently. Self-healing is acceptable only for known-volatile decorative regions, never for action targets.
- **One strategy per project, stated.** Mixed strategies are fine only if the priority order below is the rule everywhere.

## Priority order

1. **`data-testid`** - explicit contract, stable across refactors, invisible to users. Default for action targets.
2. **Role + accessible name** (`getByRole('button', { name: 'Pay' })`) - tests what assistive tech sees; also feeds `a11y-in-every-test`.
3. **Label** (`getByLabel`) - form fields.
4. **Text** (`getByText`) - for content assertions, not for clicking actions.
5. **CSS / XPath** - last resort, and only inside a page object so the blast radius is one line.

## Workflow

1. **Audit the current mix:** count selectors per type in the suite. If CSS/XPath dominate action targets, that is the debt.
2. **Agree the order** (above) and write it in the test README or `designing-test-automation-architecture` decision record.
3. **Add `data-testid` at the source** for the top 10 most-changed flows; do not retrofit the whole app at once.
4. **Move stray CSS selectors into page objects** (`refactor-to-page-objects`) so each is isolated to one line.
5. **Decide on self-healing** (`self-healing-locators`): allowed only for explicitly listed volatile regions, with a log line per heal so healed selectors are visible in the report.

## Red Flags

- selectors coupling to class names or DOM structure (`div > div > button`)
- self-healing enabled globally with no allowlist
- the same element located three different ways across the suite
- a green suite after a UI rename (means selectors were too loose or healing hid it)

## Related Skills

- `self-healing-locators` - the healing mechanism and its allowlist discipline
- `refactor-to-page-objects` - isolating selectors into page objects
- `writing-playwright-tests-best-practices` - locator conventions in context
- `stabilizing-flaky-tests` - when selector brittleness shows up as flakes
- `a11y-in-every-test` - role-based selectors double as accessibility checks

## Definition of Done

- the priority order is written down and visible in the suite's top flows
- no CSS/XPath selector outside a page object for action targets
- self-healing, if used, is allowlisted and logged per heal
- selector-related flakes trend down over the next two releases

## Rules

- One emoji per header, bullet or status cell. Never two in a row, never mid-sentence.
- Emoji belong in prose and markdown artifacts only — never in code identifiers, test names, file names, commit messages or branch names.
- The emoji must point at the meaning; if a reader has to ask what it stands for, use a word instead.
- Blanket emoji ban overrides this section where the destination enforces it (e.g. generated OpenAPI YAML, CSV, JSON).
- Prefer **one emoji per row** in tables; in narrow contexts, a single emoji can carry the row's status.
