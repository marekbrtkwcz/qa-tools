# Example Configs - Static Code Analysis for TypeScript

Practical baseline snippets for Node.js + TypeScript repositories using Biome (Playwright-flavored where noted).

> Version note: `npx biome init` generates the `$schema` reference matching your installed Biome version. Keep `@biomejs/biome` exact-pinned (`npm install -D -E`), and never hand-edit the schema version to something you do not have installed.

## Example `biome.json`

Baseline generated by `npx biome init`, with the VCS block filled in:

```json
{
  "$schema": "https://biomejs.dev/schemas/latest/schema.json",
  "vcs": {
    "enabled": true,
    "clientKind": "git",
    "useIgnoreFile": true,
    "defaultBranch": "main"
  },
  "files": { "ignoreUnknown": false },
  "formatter": { "enabled": true, "indentStyle": "tab" },
  "linter": {
    "enabled": true,
    "rules": { "preset": "recommended" }
  },
  "javascript": { "formatter": { "quoteStyle": "double" } },
  "assist": {
    "enabled": true,
    "actions": { "source": { "organizeImports": "on" } }
  }
}
```

**Key design decisions:**

- `vcs.enabled` + `useIgnoreFile` - Biome reuses `.gitignore` (and `.git/info/exclude`) instead of maintaining a second ignore list; the quick start leaves this off, so fill it in explicitly
- `defaultBranch` - set it to the repo's real default branch so `biome check --changed` and CI know the baseline to diff against
- one file covers linting, formatting, and import organization - no `eslint.config`, `.prettierrc`, `.prettierignore`, `.eslintignore`, or import-sort plugin configs
- `formatter.indentStyle` and `javascript.formatter.quoteStyle` are style picks, not requirements - change them to match the team, but change them **once**, in one place

**Ignoring generated artifacts:** with `useIgnoreFile: true`, folders listed in `.gitignore` (typically `playwright-report/`, `test-results/`, `node_modules/`) are already skipped. Use an override only for generated folders that are committed to the repo:

```json
"overrides": [
  {
    "includes": ["playwright-report/**", "test-results/**"],
    "formatter": { "enabled": false },
    "linter": { "enabled": false }
  }
]
```

**Catch missing `await` in a Playwright suite (type-aware):** a missing `await` on an assertion lets the test pass before the assertion runs. Biome's `noFloatingPromises` belongs to the `nursery` group and uses Biome's own type inference (no `tsc` project service needed). Enable it by name, on top of the recommended preset:

```json
"linter": {
  "rules": {
    "preset": "recommended",
    "nursery": { "noFloatingPromises": "error" }
  }
}
```

Nursery rules can change behavior between releases - keep the rule named and justified in the config or docs.

**Style override if the team prefers Prettier defaults:** teams migrating from Prettier usually keep `"formatter": { "indentStyle": "space", "indentWidth": 2 }` and `"javascript": { "formatter": { "quoteStyle": "single", "semicolons": "always" } }` if that matches their old `.prettierrc`, then reformat once (`biome check --write .`) and never touch it again.

## Example `package.json` quality section

This example mirrors the recommended architecture:

- Full-project format and lint in one pass
- Non-mutating CI check (`biome ci`)
- Staged-file formatting/linting
- Explicit Node engine

```json
{
  "scripts": {
    "check": "biome check --write . && npm run tsc:check",
    "check:ci": "biome ci . && npm run tsc:check",
    "format": "biome format --write .",
    "format:check": "biome format .",
    "lint": "biome lint .",
    "lint-staged": "lint-staged",
    "tsc:check": "tsc --noEmit --pretty"
  },
  "engines": {
    "node": ">=20"
  },
  "lint-staged": {
    "*.{js,mjs,cjs,jsx,ts,tsx,json,jsonc}": "biome check --write --no-errors-on-unmatched",
    "*.{css,graphql}": "biome check --write --no-errors-on-unmatched"
  }
}
```

Set `engines.node` to the Node versions your team and CI actually support - check each tool's documented minimum. The `scripts` entries point at the locally installed `@biomejs/biome` binary.

Install dev dependencies at the latest stable versions:

```bash
npm install -D -E @biomejs/biome
npm install -D typescript husky lint-staged
```

**Script naming conventions:**

| Script         | Purpose                                       | Mutates files?  | Use in CI? |
| -------------- | --------------------------------------------- | --------------- | ---------- |
| `check`        | Local aggregate: format + lint + organize     | Yes (`--write`) | No         |
| `check:ci`     | CI aggregate: `biome ci` + `tsc --noEmit`     | No              | Yes        |
| `format`       | Apply formatting                              | Yes             | No         |
| `format:check` | Validate formatting                           | No              | Yes        |
| `lint`         | Lint only, non-mutating                       | No              | Yes        |
| `lint-staged`  | Staged-file checks                            | Yes (fix mode)  | No         |
| `tsc:check`    | TypeScript type checking                      | No              | Yes        |

## Example Husky hook (`.husky/pre-commit`)

Two valid variants - pick one:

```sh
# Variant 1: no lint-staged dependency
npx biome check --staged --write
```

```sh
# Variant 2: with lint-staged (partial staging support)
npm run lint-staged
```

Put `tsc` on pre-push or CI when full type checking is too slow for every commit:

```sh
# .husky/pre-push
npm run tsc:check
```

## Example `tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ESNext",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "sourceMap": true,
    "noEmit": true,
    "baseUrl": "."
  }
}
```

**Key design decisions:**

- `module: "ESNext"` - aligns with ESM syntax used throughout TypeScript source files (`import`/`export`). Avoids the inconsistency of targeting modern JS with `target: "ESNext"` while using a legacy module system.
- `moduleResolution: "bundler"` - required when `module` is `"ESNext"`. Without it, TypeScript falls back to `"classic"` resolution which does not understand `node_modules`. The `"bundler"` strategy is the correct choice when TypeScript does not emit code (e.g. `noEmit: true`) and files are processed by a bundler or test runner (Playwright uses ESBuild internally).
- `noEmit: true` - TypeScript is used only for type checking, not code generation.
- Path aliases (`paths`) are optional - only add them when justified by project structure. If used, ensure they are also supported by the test runner.

**Why not `"module": "CommonJS"`?**

Using `"module": "CommonJS"` with `"target": "ESNext"` is a legacy pattern. It causes TS to default to `moduleResolution: "node"` (Node.js CJS algorithm), which works but is semantically incorrect for projects that:

- Use ESM `import`/`export` syntax exclusively
- Never emit code (so the module format is irrelevant for output)
- Are processed by modern tooling (ESBuild, Vite, Playwright)

If migrating from `CommonJS` to `ESNext`, the only required change is adding `"moduleResolution": "bundler"` alongside the module change.

Biome does not type-check, so this section stays just as important as it was before migrating.

## Example VS Code settings (`.vscode/settings.json`)

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "biomejs.biome",
  "[typescript]": {
    "editor.defaultFormatter": "biomejs.biome"
  },
  "typescript.preferences.importModuleSpecifier": "non-relative"
}
```

**Important:** Do NOT enable VS Code's built-in `source.organizeImports` in `codeActionsOnSave`.
VS Code's own organize-imports produces a different order than Biome's `organizeImports` assist action, causing competing re-orderings on save. Let Biome own import order - via the extension in real time and via `biome check --staged --write` on commit. Remove `esbenp.prettier-vscode` and `dbaeumer.vscode-eslint` from recommendations when doing a migration; both fight the Biome extension for formatter control.

## Example CI workflow - integrated into existing pipeline (PREFERRED)

When the repository already has a CI workflow (e.g. for Playwright tests), add a `quality` job to that workflow and make the test job depend on it:

```yaml
jobs:
  quality:
    name: Biome & Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          # match the version range declared in package.json engines.node
          node-version-file: 'package.json'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Biome (lint, format, assist)
        run: npm run check:ci

  test:
    needs: quality
    # ... existing test job configuration ...
```

`biome ci` prints GitHub annotations on GitHub hosts and cannot mutate files, which makes it the right CI command - `biome check` is for local use.

## Example CI workflow - standalone (FALLBACK)

Use this only when the repository has **no existing CI workflow** to integrate into:

```yaml
name: Quality Gate

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  quality:
    name: Biome & Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version-file: 'package.json'
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Biome (lint, format, assist)
        run: npm run check:ci
```

**Alternative without an npm install:** the first-party `biomejs/setup-biome@v2` action installs the Biome binary directly (`uses: biomejs/setup-biome@v2` with a pinned `version:`, then `run: biome ci .`). Prefer it only for jobs that install no npm dependencies - otherwise the npm-installed run above keeps CI on the repo's exact-pinned version.

## Example GitLab CI job

For GitLab, the official Docker image avoids a Node setup entirely:

```yaml
stages:
  - quality

biome:
  image:
    name: ghcr.io/biomejs/biome:latest
    entrypoint: [""]
  stage: quality
  script:
    - biome ci --reporter=gitlab --colors=off > code-quality.json
  artifacts:
    reports:
      codequality: code-quality.json
  rules:
    - if: $CI_COMMIT_BRANCH
    - if: $CI_MERGE_REQUEST_ID
```

Pin the image to an exact tag (`ghcr.io/biomejs/biome:2.x.y`) instead of `latest` so CI matches the repo's pin, and keep `tsc --noEmit` in a separate Node-based job - the Biome image ships no `tsc`.

**CI design principles:**

- Every command is non-mutating - `biome ci` has no write mode by design
- `npm ci` ensures reproducible installs
- Node version matches `engines.node` from `package.json`
- `permissions: contents: read` follows least-privilege principle
- **Prefer integrating into an existing pipeline** - only use a standalone workflow as a fallback
