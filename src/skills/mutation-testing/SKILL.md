# Mutation Testing

Use this skill when a green suite has to prove it can fail. Mutation testing answers the question coverage cannot: not "did the tests run this line" but "if this line were wrong, would a test catch it".

It works by seeding small defects (mutants) into the product code and running the suite against each: a mutant killed by a failing test proves the assertion; a mutant that survives proves a hole, no matter how high the coverage says the file is. For suites written or bulk-generated by an AI agent this is the cheap deterministic check on output quality - `unslop-tests` suspects a tautological test by reading it, mutation testing convicts it by running it.

## When to Use

- Judging whether tests — including AI-generated ones — assert anything real
- Hardening a suite after coverage plateaued
- Wiring a mutation gate into CI
- Deciding mutation testing is not worth it for this repo yet
- A green suite has to prove it can fail

## When NOT to Use

- The suite is red or flaky - fix that first; mutation results on an unstable suite are noise.
- The repo has no meaningful assertions at all yet (smoke-only) - write assertions first; every mutant would survive.
- Somebody asks for a coverage percentage - that is `analyzing-quality-metrics`; mutation score is a different, sharper statement.
- The product is mostly declarative data or generated code - mutating generated output proves nothing about tests.

## Recommended Outcome

A run using this skill should end with:

- a baseline mutation score for the chosen scope (whole suite or the diff), from the runner's report (Stryker for JS/TS)
- every survivor triaged into one of three categories (see the procedure) - not just counted
- tests added where the triage says the suite under-asserts, with the re-run proving the mutants now die
- an explicit, written policy for whether and where this becomes a CI gate - and if not, why not
- cost settings (scope, concurrency, incremental mode, threshold break) recorded so the next run is reproducible

## Procedure

### 1. Confirm the suite is a fit

Before running anything, check that:

- the suite is deterministic and green (`npm test` twice in a row, no flakes)
- the target scope contains real logic (parsing, calculations, state transitions, API request building) rather than pure wiring
- the runner is supported: StrykerJS ships runners for Jest and Vitest among others; Playwright and custom runners run through the generic `command` runner (examples in `./resources/stryker-js-ts.md`)

If any check fails, stop and report which one - mutation testing a flaky suite produces expensive noise.

### 2. Choose the scope

Cost scales linearly with mutants times test time, so scope deliberately:

- **Audit mode (default)**: mutate one risk area (the module a release depends on, the code the agent just wrote tests for), not the whole repo
- **Diff mode**: mutate only files changed in the branch (`"mutate"` globs from the diff) - the proportionate gate for pull requests
- **Full mode**: reserve for nightly or pre-release runs on repos where the suite is fast or parallel

### 3. Run and read the baseline

Run Stryker on the chosen scope and read the four outcomes, not just the score:

| Outcome | Meaning | Action |
| --- | --- | --- |
| killed | a test failed on the mutant | the suite earns its keep here |
| survived | all tests stayed green on broken code | triage (step 4) |
| no coverage | no test even executed the mutant | coverage gap - fix before judging assertions |
| timeout | the mutant caused a hang, treated as detected | check it is not an infra flake |

Record the score and the raw counts separately: `83% (killed 99/120, 14 survived, 7 no coverage)` says where the work is; `83%` alone hides whether the hole is assertions or coverage.

### 4. Triage every survivor

For each surviving mutant, decide which one it is and act:

1. **Under-asserting suite (the common case)** - the code matters, the test does not pin it: write or strengthen one test that kills the mutant, and re-run to see it die
2. **Equivalent mutant** - the program behavior is genuinely identical (e.g. `>` mutated to `>=` at an unreachable boundary): document it in the run record with one sentence why; never "fix" the code to please a tool
3. **Dead/unreachable code** - the mutant is on a path no caller can reach: route the finding to `tech-debt-analysis` or delete the code; do not write a test for it

Do not bulk-disable operators or mute whole directories to make the number look better - that is the lint-disable antipattern in a different tool (`governing-quality-waivers` treats it the same way).

### 5. Wire CI only after the baseline earns it

A mutation gate makes sense only after the baseline is known and the survivors are triaged:

1. add the run as a scheduled job first (nightly), reporting the score as a trend (`tracking-quality-trends`), not a pass/fail
2. only then consider a diff-scoped gate on pull requests with a modest `thresholds.break` low enough to catch deletions of assertions (see `./resources/stryker-js-ts.md`)
3. keep the gate on changed code, with a timeout budget; a whole-repo mutation gate that takes hours gets disabled within a month

### 6. Report

State, in this order: the score with its denominator, the split of survivors into the three triage categories, what changed (tests added / mutants documented as equivalent), the cost of the run (minutes, CI minutes), and the recommendation: gate now, gate on diff only, or re-audit after the next bulk test change.

## Decision Rules

**Prefer diff-scoped runs when:** the suite takes minutes to run; pull requests are the review unit; the repo is larger than one module.

**Prefer scheduled whole-suite runs when:** the suite is fast (< a few minutes) or the repo is small; the question is overall suite health trending, not one change.

**Prefer example runs (no gate) when:** the team has no mutation culture yet - one audited module with a written report recruits more believers than an instantly-red CI job no one understands.

**Treat the mutation score as a trend metric, not a vanity number when:** reporting to stakeholders - show its movement and what the survivors were, not a single percentage (the `analyzing-quality-metrics` gaming caveats apply here doubled).

**Be extra suspicious after AI-generated test batches when:** an agent produced many tests quickly - sample the changed modules with a mutation run before believing the coverage report; agents satisfy coverage metrics the way water flows downhill.

**Treat surviving-mutant counts on generated code as noise when:** the mutant target is generated output, vendored code, or lockfiles - exclude them in `mutate` globs.

## AI-Agent Notes

- When this skill runs after an agent wrote tests, triage survives into the same three categories before criticizing the agent's work: an equivalent mutant is not a test bug.
- Do not let the same agent that wrote the tests both run mutation testing and then "fix" survivors by weakening assertions or deleting mutants from scope - the `red-test-deletion-guard` hook and `governing-quality-waivers` exist for exactly that shape; report scope changes in the run record.
- A mutation run is evidence: save the HTML report path or the JSON summary, and quote survivor locations (`file:line`) in the report the way a bug report quotes repro steps.

## Completion Checklist

- [ ] Scope chosen explicitly (module / diff / full) and recorded
- [ ] Baseline run completed with the outcome split, not just the score
- [ ] Every survivor triaged: test written, equivalence documented, or routed to debt removal
- [ ] Re-run proves the newly written tests kill their mutants
- [ ] CI policy decided and stated (gate / scheduled report / revisit-later), with settings recorded
- [ ] Report names cost, score with denominator, survivor categories, and next step

## Definition of Done

A task using this skill is complete when the report answers, with evidence: what the suite provably catches in the chosen scope, what it provably does not, which of those were test gaps (now fixed and killed on re-run) versus equivalent mutants (documented), what the run cost, and what the CI recommendation is.
